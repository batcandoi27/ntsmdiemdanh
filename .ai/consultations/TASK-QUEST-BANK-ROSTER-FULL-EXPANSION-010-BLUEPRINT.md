# 2\. Thuật toán giao nhiệm vụ tuần deterministic

### Nguyên tắc

Mỗi học sinh:

- chỉ nhận **1 nhiệm vụ chính / tuần**;
- không có nút "Tự chọn nhiệm vụ";
- cùng một `studentId + week + year` luôn cho cùng kết quả;
- sang tuần mới sẽ tự động có nhiệm vụ mới;
- seed không được dùng ID hiển thị cho học sinh;
- nên dùng hash ổn định như **SHA-256**, không dùng JavaScript `Math.random()`.

Có thể thiết kế theo công thức:

```
weekKey = ISO_WEEK(year, date)
seedInput = studentId + ":" + weekKey + ":" + year
seed = SHA-256(seedInput)

categoryIndex = seedInt(seed[0..7]) % 4
questIndex = seedInt(seed[8..15]) % 20

quest = QUEST_BANK[categoryIndex][questIndex]
```

Tuy nhiên, nếu chỉ lấy `% 20`, một học sinh có thể nhận lại cùng nhiệm vụ ở nhiều tuần khác nhau. Vì vậy nên dùng **seeded permutation** để phân tán 20 nhiệm vụ trước khi quay vòng.

### Khuyến nghị tốt hơn

```
seed = SHA-256(studentId + ":" + weekOfYear + ":" + year)

category = hashToInt(seed, 0) % 4

permutationSeed = hashToInt(seed, 1)

questIndex = permutation(
    [0..19],
    permutationSeed
)[weekCycle]
```

Trong đó `weekCycle = floor(weekOfYear / 4)` hoặc một cơ chế cycle tương đương.

Kết quả có các tính chất:

1. **Deterministic:** cùng input → cùng nhiệm vụ.
2. **Không random lại khi refresh:** reload trang vẫn giữ nhiệm vụ.
3. **Không phụ thuộc thứ tự database:** ID nhiệm vụ không được thay đổi ngẫu nhiên mỗi lần query.
4. **Có thể audit:** giáo viên có thể tính lại assignment từ `studentId`, tuần và năm.
5. **Phân bổ đều:** không để một vài quest được giao quá nhiều.

### Pseudocode

```
function assignWeeklyQuest(studentId, date):
    year = getYear(date)
    week = getISOWeek(date)

    seed = SHA256(studentId + ":" + year + ":" + week)

    categoryIndex = toUInt32(seed[0:4]) % 4

    questBank = QUEST_BANK[categoryIndex]

    cycle = floor((week - 1) / 4)
    permutationSeed = SHA256(seed + ":" + cycle)

    questIndex = seededPermutation(
        range(0, 19),
        permutationSeed
    )[ (week - 1) % 20 ]

    return questBank[questIndex]
```

Ở tầng database, nên lưu assignment đã phát sinh:

```
weekly_quest_assignments
--------------------------------
id
student_id
year
iso_week
quest_id
assigned_at
status
submission_id
```

Tạo unique constraint:

```
UNIQUE(student_id, year, iso_week)
```

Như vậy kể cả hai request đồng thời cũng không thể tạo hai nhiệm vụ cho cùng học sinh/cùng tuần.

# 3\. Luồng nộp bài và cập nhật minh chứng

Không nên khóa submission ngay khi học sinh nhấn "Nộp".

Nên dùng state machine:

```
ASSIGNED
    ↓
IN_PROGRESS
    ↓
SUBMITTED
    ↓
REVISION_ALLOWED
    ↓
SUBMITTED
    ↓
GRADED
```

### Quy tắc

**Trước khi giáo viên chấm:**

- học sinh xem lại toàn bộ nội dung;
- sửa description/reflection;
- thay thế hoặc bổ sung minh chứng;
- có thể lưu nháp;
- nhấn `Cập nhật minh chứng` để tạo phiên bản mới.

**Sau khi giáo viên bắt đầu chấm:**

- khóa chỉnh sửa;
- giữ nguyên snapshot được giáo viên chấm;
- nếu giáo viên yêu cầu bổ sung, chuyển về `REVISION_ALLOWED`;
- mọi lần thay đổi phải có version/audit log.

Schema đề xuất:

```
quest_submissions
-----------------------------
id
assignment_id
student_id
content
status
submitted_at
graded_at
current_version

quest_submission_versions
-----------------------------
id
submission_id
version_no
content
evidence_urls
created_at
created_by
```

Điểm quan trọng: **không overwrite minh chứng cũ**. Mỗi lần cập nhật tạo version mới để giáo viên có thể biết học sinh đã sửa gì.

### Sinh nickname

Có thể tạo nickname deterministic một lần từ secret server-side:

```
nicknameSeed = HMAC_SHA256(
    SERVER_SECRET,
    studentId
)

animal = ANIMALS[nicknameSeed % ANIMALS.length]
adjective = ADJECTIVES[
    (nicknameSeed >> 8) % ADJECTIVES.length
]

nickname = adjective + " " + animal
```

Nếu lớp tăng lên 44, 45, 50 học sinh thì generator tiếp tục cấp vị trí mới, **không cần sửa code UI**.

# 7\. Generator căn cứ tổng quát

Thay vì tạo thủ công 43 record, nên có hàm:

```
generateBaseSlots(studentCount):
    zones = ["A", "B"]
    floors = [1, 2, 3, ...]

    slots = []

    for zone in zones:
        for floor in floors:
            for position in 1..MAX_PER_FLOOR:
                slots.push({
                    zone: zone,
                    floor: floor,
                    position: position,
                    baseCode:
                        zone + "-" + floor + pad(position)
                })

    return slots.slice(0, studentCount)
```

Sau đó:

```
students = getAllActiveStudents()

slots = generateBaseSlots(students.length)

for i in 0..students.length-1:
    assign(students[i], slots[i])
```

**Không dùng `slice(0, 28)` ở bất kỳ tầng nào.**

# 8\. Nguyên tắc phân bổ thông minh

Để bản đồ không bị dồn hết học sinh vào một khu:

```
student #1  → A-101
student #2  → B-101
student #3  → A-102
student #4  → B-102
...
```

Tức là **round-robin giữa A/B**, sau đó tăng tầng.

Ví dụ:

| Học sinh thứ | Khu | Tầng | Vị trí |
| --- | --- | --- | --- |
| 1 | A | 1 | 01 |
| 2 | B | 1 | 01 |
| 3 | A | 1 | 02 |
| 4 | B | 1 | 02 |
| 5 | A | 1 | 03 |
| 6 | B | 1 | 03 |
| ... | ... | ... | ... |
| 43 | A/B theo vòng | tầng tiếp theo | vị trí tiếp theo |

Nếu cần bảo toàn căn cứ cũ, **không tái phân bổ toàn bộ mỗi lần roster thay đổi**. Chỉ cấp slot mới cho học sinh mới.

## 10\. Acceptance criteria

Hệ thống được xem là đạt khi:

- **80/80 nhiệm vụ** tồn tại và có đủ `Title + Description + Category + XP + Xu + Hint`.
- Mỗi nhóm có **20 nhiệm vụ**.
- Mỗi học sinh có **chính xác 1 quest/tuần**.
- Refresh/reload không làm nhiệm vụ thay đổi.
- Cùng `studentId + week + year` luôn cho cùng assignment.
- Không có nút cho học sinh tự chọn quest.
- Submission có thể xem lại và cập nhật minh chứng **trước khi giáo viên chấm**.
- Có version/audit trail cho các lần cập nhật.
- Leaderboard **không trả student ID**.
- Leaderboard chỉ hiển thị `anonymous nickname + mascot/icon + XP`.
- 43 học sinh tạo được **43/43 căn cứ**.
- Không còn giới hạn hard-code 28.
- Thêm học sinh thứ 44/45 không làm mất căn cứ của học sinh cũ.
- Slot căn cứ phân bổ cân bằng giữa **Khu A/B và các tầng**.
- `student_id`, nickname và base assignment có unique constraint phù hợp.

**Kết luận kiến trúc:** nên coi `QuestBank`, `WeeklyAssignment`, `SubmissionVersioning`, `AnonymousIdentity` và `BaseRegistry` là 5 lớp dữ liệu độc lập. Cách này vừa đáp ứng ngân hàng 80 nhiệm vụ, giao quest deterministic, bảo vệ danh tính trên leaderboard, vừa loại bỏ hoàn toàn giới hạn 28 căn cứ khi roster tăng lên 43+ học sinh.
