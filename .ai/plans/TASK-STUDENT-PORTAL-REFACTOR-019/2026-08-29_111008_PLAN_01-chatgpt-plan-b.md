# 1\. Plan B — Independent architecture and product vision

### Core product principle

> **The Student Portal should make a child feel that returning, learning, improving and belonging are intrinsically rewarding—not that losing momentum makes them lose status.**

This leads to five architectural invariants:

1. **No punitive state transitions**
   
   - No level decay.
   - No starvation.
   - No punishment for inactivity.
   - No negative progression caused merely by absence.
2. **No educational advantage for virtual possessions**
   
   - Forge/shop items cannot increase XP, grades, assessment scores or learning multipliers.
   - Cosmetics may communicate identity and achievement, but never academic power.
3. **Evidence ≠ completion ≠ assessment**
   
   - These are separate concepts in both UX and data.
   - A completed quest does not automatically become an officially assessed result.
   - No implicit `score_achieved = 10`.
   - Verification status must be explicit and auditable.
4. **Child agency without child exposure**
   
   - Children can express themselves through spaces, cosmetics, companions and achievements.
   - They should not need to expose their home, location, private household or sensitive personal circumstances.
5. **Social motivation without public humiliation**
   
   - Default experience is personal growth.
   - Collective activities should reward contribution and appreciation.
   - Competitive ranking can exist only as a deliberate/appropriate mode, not as the psychological baseline.

# 8\. Quest verification — four proportional evidence tiers

The four-anchor system should become a **confidence ladder**, not an “AI-proof” system.

| Tier | Evidence | Use |
| --- | --- | --- |
| 1 | Self-report | Low-risk routine activities |
| 2 | Form / Quiz | Knowledge or structured response |
| 3 | Artifact | Work product when genuinely needed |
| 4 | Random check | Sampling for integrity |

### Critical rule

**Verification confidence is not the same as academic score.**

For example:

```
completion = TRUE
verification_status = PENDING
score_achieved = NULL
```

is valid.

So is:

```
completion = TRUE
verification_status = VERIFIED
score_achieved = NULL
```

And:

```
completion = TRUE
verification_status = VERIFIED
official_assessment_status = ASSESSED
score_achieved = 8.5
```

Only the last state represents an official assessment result.

# 9\. Database invariants

The existing requirement explicitly identifies:

```
physical_anchor_verified DEFAULT TRUE
```

as dangerous.

Plan B recommendation:

```
physical_anchor_verified DEFAULT NULL
```

with semantic meaning:

```
NULL  = not yet checked / pending
FALSE = checked and not verified
TRUE  = verified
```

Do **not** overload `NULL` to mean failure.

Prefer an explicit state machine if schema evolution allows it:

```
verification_status:
  NOT_REQUIRED
  PENDING
  VERIFIED
  REJECTED
```

This is safer than boolean ambiguity.

### Completion/assessment separation

Recommended conceptual schema:

QuestAttempt
- id

- quest_id
- completed_at
- completion_status
- verification_status
- evidence_type
- evidence_ref
- assessed_at
- assessed_by
- assessment_status
- score_achieved

`score_achieved` should be nullable.

# 12\. Webhook hardening

This is one of the highest-priority technical changes.

The requirement:

> Replace `getLastRow()` with event range values.

is correct.

### Anti-pattern

JavaScript

```
const row = sheet.getLastRow();
const values = sheet.getRange(row, 1, 1, sheet.getLastColumn()).getValues()[0];
```

This is race-prone because another write may occur between the event and processing.

### Preferred model

Consume the values belonging to the actual event/range supplied by the event source.

Conceptually:

```
event
 ├── range
 ├── values
 ├── timestamp
 └── source metadata
```

Then add:

```
HMAC signature
timestamp / freshness window
nonce
idempotency key
```

### Verification flow

```
receive webhook
       ↓
validate required fields
       ↓
validate timestamp window
       ↓
validate HMAC
       ↓
check nonce / replay cache
       ↓
derive idempotency key
       ↓
atomic "already processed?" check
       ↓
process reward
       ↓
persist processing record
```

### Reward invariant

```
same event + same idempotency key
        ≠
two rewards
```

The reward operation must be **idempotent**.

# 13\. Reward transaction design

Do not implement:

```
verify event
→ increment XP
→ separately insert log
```

without protection against retries.

Prefer a transactional/outbox-style pattern:

```
RewardEvent
- idempotency_key UNIQUE
- event_id
- student_id
- reward_type
- amount
- received_at
- processed_at
- status
```

Then:

```
INSERT RewardEvent
       ↓
UNIQUE constraint
       ↓
first request = process
retry = no-op / return prior result
```

If the underlying datastore cannot provide a true transaction, emulate idempotency with a durable uniqueness constraint and carefully ordered state transitions.
